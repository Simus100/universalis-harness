Il modello del simulatore

Nessun numero qui è una misura: sono conseguenze aritmetiche di ipotesi dichiarate. Servono a rendere visibile l'ordine di grandezza delle scelte del report.

Oggi (as-is)

  • Contesto = 6000 di prefisso + conversazione; le osservazioni entrano intere.
  • Compaction quando il contesto supera finestra − 16384: il riassunto tiene il 15% della storia.
  • Ogni cambio di gate azzera la cache per quel passo (il prefisso è stato ricostruito).
  • Errore recuperato nel 40% dei casi; ogni recupero costa 2 passi di retry alla cieca.
  • Quota letta da cache: 0,55 normale · 0 nel passo di cambio gate · 0,20 dopo una compaction.

Proposto (to-be)

  • Prefisso stabile: i tool si mascherano, non si rimuovono → cache conservata.
  • Osservazioni oltre 2.000 token → riferimento da 150 token, contenuto su file rileggibile.
  • Recitation: 300 token in coda ogni 5 passi; riduce del 25% gli errori e la deriva.
  • Compaction alla soglia scelta, riassunto con decisioni ed errori: tiene il 35% della storia.
  • Errore classificato → riparazione mirata: recupero all'85%, un solo passo di retry.
  • Quota letta da cache: 0,90 normale · 0,79 dopo una compaction.
  • Due volte su cinque l'agente rilegge 2.000 token dal file scaricato: è il costo dell'offload, contato.
  • Ogni passo porta con sé il ragionamento (400 token), uguale nei due rami.
Onestà del modello. Costo = token non in cache × prezzo + token in cache × 10% + output × 3 × prezzo. Latenza = 0,35 s di base + 0,02 s ogni 1.000 token non in cache + 0,6 s per ogni retry. Gli eventi casuali (errori, cambi di gate) sono gli stessi nei due rami, così il confronto è onesto. Ciò che il simulatore non sa: la qualità della risposta. Per quella serve un set di casi d'oro (P1 del report).
